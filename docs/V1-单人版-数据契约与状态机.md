# V1 单人本地版：数据契约与状态机（冻结稿）

> 来源：Claude 对《AI 需求管理工作台 V1 产品与技术架构方案》的只读审查。范围：本地单用户、SQLite、手动交接，不含 Runner、云端、多用户。
> 实现位置：`server/`（领域层，无 HTTP、无界面）；测试：`tests/domain/`。HTTP 与页面接入由后续阶段完成。

## 1. 范围

**做**：需求、任务、依赖、启动任务时的不可变上下文快照、Run 记录、验收/退回、追加式事件、旧 localStorage 数据迁移、JSON 导出 v2、数据库备份。

**不做（V2）**：Runner 领取/心跳/租约、`artifacts`、`resource_leases`、AI 自动拆分、全局上下文编辑界面、云端同步、多用户、需求七段生命周期。

## 2. 任务状态（六个，沿用原型）

| 状态 | 含义 |
|---|---|
| `clarification` | 待澄清 |
| `queued` | 待执行（就绪后可启动） |
| `working` | 执行中（必有且只有一个 `running` 的 Run） |
| `review` | 已提交结果，待人工验收 |
| `done` | 人工验收通过 |
| `blocked` | 阻塞（必须有原因） |

失败是 **Run** 的结果，不是任务状态。Run 状态：`running` → `succeeded` / `failed` / `cancelled`。

### 2.1 流转表

“方式”列是进入目标状态的唯一入口；通用 `transitionTask` 只处理标记为“通用”的行。

| 从 | 到 | 方式 | 必填 |
|---|---|---|---|
| clarification | queued | 通用 | — |
| clarification | blocked | 通用 | 原因 |
| queued | clarification | 通用 | — |
| queued | blocked | 通用 | 原因 |
| queued | working | `startTask` | 依赖未验收时需 `overrideReason` |
| working | review | `submitResult` | 结果摘要 |
| working | queued | 通用（取消运行） | 原因；当前 Run 置 `cancelled` |
| working | queued | `reportFailure`（失败） | 失败信息；当前 Run 置 `failed` |
| working | blocked | 通用（取消运行） | 原因；当前 Run 置 `cancelled` |
| review | done | `acceptTask` | — |
| review | queued | `rejectTask` | **修改意见** |
| review | blocked | 通用 | 原因 |
| done | queued | `reopenTask` | **重开原因** |
| blocked | queued | 通用 | — |
| blocked | clarification | 通用 | — |

任何不在表内的组合，或试图用通用流转进入 `working` / `review` / `done`，都返回 `ILLEGAL_TRANSITION`，数据与事件均不变。

## 3. 就绪条件

`getReadiness(taskId)` 返回 `{ ready, blockers[], warnings[] }`。

- 阻塞项（不可越过）：状态不是 `queued`（`NOT_QUEUED`）。
- 阻塞项（带原因可越过）：存在未 `done` 的依赖（`DEPENDENCY_NOT_DONE`）、关联需求已删除（`REQUIREMENT_DELETED`）。
- 仅提示：验收标准为空、未填执行人。迁移来的任务没有这些字段，不能因此无法启动。

## 4. 启动任务（唯一进入 `working` 的路径）

一个事务内完成：校验 → 生成快照 → 创建 Run（`attempt = 已有最大值 + 1`）→ 任务置 `working`、`revision + 1` → 写事件。任一步失败整体回滚。数据库用部分唯一索引保证同一任务同时只有一个 `running` Run。

快照在数据库层不可修改、不可删除（触发器）。内容见 §6。

## 5. 数据模型（`server/migrations/0001_init.sql`）

| 表 | 要点 |
|---|---|
| `workspaces` | 固定一行 `WS-LOCAL` |
| `workspace_context_versions` | 追加式；种子为空规则；快照引用其 `revision` |
| `requirements` | `revision`、软删除 `deleted_at`；保留旧 `REQ-xxxxx` ID；`decision` 沿用 pending/keep/modify/defer/delete |
| `tasks` | `requirement_id` 可空（迁移孤儿任务）；`provider`（模型）与 `executor_type`（执行方式）分开；`blocked_reason`；`acceptance_json`、`file_scope_json` |
| `task_dependencies` | `(task_id, depends_on_task_id)`；服务层拒绝自依赖与循环 |
| `task_context_snapshots` | 不可变；`payload_json` + `prompt_text` + `payload_hash`（规范 JSON 的 SHA-256）+ 各 revision |
| `task_runs` | 失败重试另建 Run；`snapshot_id` 仅旧数据 Run（`is_legacy=1`）可空；含结果、证据、错误、验收结论 |
| `events` | 追加式（不可改/删）；自增 ID；`payload_json` 含 from/to/reason/before/after |
| `migration_sources` | 旧数据来源：载荷哈希（唯一）、原始载荷、迁移报告 |

约定：时间一律由应用层写入 UTC ISO-8601（带毫秒和 `Z`），不用 SQL 默认值；`PRAGMA user_version` 记录迁移版本；外键开启；WAL。

## 6. 快照内容

```text
schema_version, prompt_template_version
workspace:    { id, revision, rules }
requirement:  { id, revision, module, title, description, target_version, decision, decision_note } | null
task:         { id, revision, provider, executor_type, assignee, task_text, acceptance[], file_scope[] }
dependencies: [{ id, status, result_summary }]
override_reason
```

`prompt_text` 是用同一份数据渲染出的最终指令。`payload_hash` 对键排序后的规范 JSON 计算。

## 7. 旧 localStorage 数据迁移规则

入口：页面把 `chuhaila.requirements.workbench.v1`（或 SQLite 单文档里的同结构）读出来，交给 `previewLegacyImport` / `commitLegacyImport`。服务端读不到浏览器存储，所以只能由页面发起。

| 旧数据 | 新数据 |
|---|---|
| `items[]` | `requirements`，ID 不变；非法 `decision` 归为 `pending` 并记警告 |
| `tasks[]` | `tasks`，ID 不变；`model` → `provider`，`executor_type = manual_handoff`；`blockedReason` → `blocked_reason` |
| `featureId` 指向不存在的需求 | `requirement_id = NULL`，保留 `legacy_requirement_title/module`，列入报告 |
| `suggestion` 非空，或状态为 `working/review/done` | 一条 `is_legacy = 1` 的 Run（无快照）：`working` → `running`，其余 → `succeeded`；`done` 同时记 `accepted` |
| `events[]` | `events`，`event_type = legacy.import`，原 ID/动作/操作人/前后值放 payload；按时间正序写入 |

规则：

1. **先预览，后提交**。预览不写库，返回新增/相同/冲突/无效计数、孤儿任务和警告。
2. **不覆盖**。同 ID 内容相同 → 计为“相同”；内容不同 → 计为“冲突”并跳过，原记录不动。
3. **可重复**。同一份载荷（哈希相同）第二次提交返回 `already_imported`，0 新增；载荷变了但 ID 已存在，同样逐条跳过。事件按旧 ID 去重。
4. **可回滚**。提交前用 `VACUUM INTO` 备份；整个导入在单个事务内，写完核对条数，对不上则整体回滚。原始载荷存入 `migration_sources`。
5. 不删除浏览器 localStorage（由页面层负责，并在覆盖前备份）。

## 8. 删除语义

需求软删除（`deleted_at`），其任务与历史保留；软删除的需求不出现在默认列表。任务启动时若关联需求已删除，需带原因越过。不提供硬删除。

## 9. 给 HTTP/页面接入阶段的接口清单

领域层方法（`createWorkbench(db)` 返回）：
`createRequirement` `updateRequirement` `deleteRequirement` `listRequirements` `getRequirement` · `createTask` `updateTask` `getTask` `listTasks` · `addDependency` `removeDependency` `getReadiness` · `startTask` `submitResult` `reportFailure` `transitionTask` `acceptTask` `rejectTask` `reopenTask` · `listRuns` `getSnapshot` `listEvents` · `exportAll`。

建议路由：`/api/requirements`、`/api/tasks`、`/api/tasks/:id/{start,transition,accept,reject,reopen}`、`/api/runs/:id/{result,failure}`、`/api/events`、`/api/export`、`/api/migrate/legacy/{preview,commit}`。写接口只收 `application/json`，校验 `Origin` 与 `Host`，更新带 `expectedRevision`，冲突返回 409。
