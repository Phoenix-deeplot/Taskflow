## 一、E 的结论：两个执行器都能调用

| 执行器 | 怎么调用 | 已验证 |
|---|---|---|
| **Claude Code** | PATH 里的 `claude -p` | `claude --version` → 2.1.284 |
| **Codex** | 安装在 `C:\Program Files\WindowsApps\OpenAI.Codex_…\app\resources\codex.exe`（你给的 `codex-windows-sandbox-service.exe` 是它的沙箱辅助服务，不是入口）。Windows 不允许外部程序直接启动商店应用包里的程序（直接运行返回 `Access is denied`），但**以应用包身份启动可以**：`Invoke-CommandInDesktopPackage`，包族名 `OpenAI.Codex_2p2nqsd0c76g0`，AppId `App` | `codex.exe --version` → `codex-cli 0.158.0-alpha.2`；`codex exec` 非交互模式存在；`login status` → 已用 ChatGPT 登录 |

Codex 这条路的注意点（给 Codex 适配器的实现者）：

- 以应用包身份启动**拿不到标准输出管道和进程号**，只能把输出重定向到文件，由 Runner 读文件尾部来取进度和日志；结束要靠退出标记文件；取消需要自己想办法结束进程树。
- 版本是 alpha，安装路径里带版本号，更新后路径会变，所以路径要每次通过 `Get-AppxPackage` 查，不能写死。
- 如果这条路不稳，退路是单独安装 Codex 命令行（会得到普通的 `codex` 命令，有标准管道），适配器接口不变。

页面本身不能启动程序，本地服务可以；所以不需要“桌面端”，现在的本地服务加 Runner 就够。

## 六、领域层已就绪（2026-10-20，给 Codex 的对接）

你要的“执行所有未完成的任务”按“开工”处理，同时也做成了功能：`dispatchAll`。我这边（领域层）的 A、C、F、G 部分已完成，`npm test` 全部通过。

| 方法 | 返回 / 行为 |
|---|---|
| `createAnalysisTask(requirementId, { template?, executorType?, provider?, assignee? })` | 创建 `kind: "analysis"` 的任务，任务说明 = 模板 + 需求详情（`server/analysis.mjs` 的默认模板，可传 `template` 覆盖）。分析任务的快照指令是“只读分析，不要修改任何文件”，`claimRun` 返回的 `task.kind` 为 `analysis`，**Runner 应以只读方式运行**。结果走原来的 `submitResult`，进“待验收”，不会自动改需求决策 |
| `dispatchTasks(taskIds, { executorType?, overrideReason? })` | `{ results: [{ taskId, ok, runId? , code?, message?, blockers? }], dispatched, skipped }`。每个任务各自独立：依赖未满足、没选执行器、状态不对的会被跳过并给出原因，**不影响其他任务**。一次最多 200 个 |
| `dispatchAll({ executorType?, requirementId?, kinds? })` | “执行所有未完成的任务”：把所有 `queued` 的任务按创建顺序派发，返回同上，并多一个 `waiting`（其余未完成任务的数量：待澄清 / 执行中 / 待验收 / 阻塞），页面可以据此提示“还有 N 个在等你”。没有可派发的任务时返回全 0，不报错 |
| `listSettings()` / `getSetting(key)` / `setSetting(key, value)` / `clearSetting(key)` | 目前只有 `project.path`（项目目录，最长 500 字）。不存在则为 `null`，Runner 回退到服务启动时的目录。**目录是否存在、是否 git 仓库由路由层检查** |
| `getRunDetail(runId)` | 页面“运行详情”所需的全部数据：`phase`（一句话状态，如“等待 Runner 领取 / 修改文件 / Runner 失联 / 执行失败”）、`progress`（`step`、`pct`、`message`、`at`）、`heartbeat`（`state`: ok / slow / lost / ended，`ageSeconds`）、`error`（`code`、`message`）、`logTail`（最近 8000 字）、`artifacts`、`attempts`（每次尝试）、`timeline`（带人话摘要） |

**进度事件规范（Runner 采集端遵守）：** `appendRunEvent(runId, token, { eventId, type, message, data })`：

- `type: "progress"`：`data` 可带 `step`（≤120 字的文本）和 `pct`（0 到 100 的数字），不合规会被拒绝。页面显示最近一条。
- `type: "log"`：`message` 是一段日志（单条 ≤4000 字），建议 Runner 每几秒攒一批发一次，不要一行一条。页面显示最近 8000 字。
- 其他 `type` 自由，只出现在时间线里。

**给页面的提醒：** 任务现在有 `kind` 字段；任务导出里目前没有带出，需要时在 `exportLegacyState` 里补上。

**补充（同日）：**

- **分析结果格式校验：** 分析任务用默认模板时，`submitResult` 会检查答案是否包含“结论 / 用户价值 / 实现复杂度 / 关键风险与依赖 / 建议的 V1 范围 / 需要我确认的问题”，结果作为一条证据（`kind: "check"`）附在 Run 上，页面验收时可以显示。**只提示，不拦截**；自定义模板不检查。
- **工作区契约（给 Runner 和适配器）：** `claimRun` 的返回里多了 `workspace`：
  - `projectPath`：项目目录设置；`null` 表示用服务启动时的目录。
  - `access`：`read-only`（分析任务）或 `write-on-branch`（执行任务）。**分析任务不得写任何文件。**
  - `branch`：执行任务必须在这个分支（或以它命名的工作树）里改文件，**不得动主分支**；分析任务为 `null`。
  - `autoApprove`：恒为 `false`，适配器不得默认打开“全部自动批准”。
  - 适配器完成后用产物回报：`kind: "branch"`（`uri: "git:<分支名>"`，`metadata: { base, commit }`）和 `kind: "diff"`（改动文件）。`getRunDetail` 的 `workspace.reportedBranch` / `workspace.diff` 会展示它们，页面验收时可直接看改动。
