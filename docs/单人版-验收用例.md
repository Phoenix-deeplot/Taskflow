> 范围：本地单用户、SQLite、手动交接，不含 Runner / 云端 / 多用户。

## 二、手动界面检查

准备：`npm run dev`，浏览器打开 `http://127.0.0.1:4179`。建议用一份可丢弃的数据库试，避免动到正在用的数据：

```powershell
$env:WORKBENCH_DATA_DIR = "$env:TEMP\workbench-acceptance"; npm run dev -- --port 4190
```

| 编号 | 步骤 | 期望 | 结果 |
|---|---|---|---|
| U1 | 新增需求 → 刷新页面 → 停止并重启服务 → 再打开 | 需求仍在 | |
| U2 | 建任务 → 启动 → 复制指令 → 填写结果提交 → 验收通过 | 看板、变更记录、任务状态三处一致 | |
| U3 | 打开任务详情 | 能看到启动时的需求内容、指令和模板版本 | 页面暂无入口（契约 §11 第 7 项） |
| U4 | 停掉服务后在页面里保存 | 提示保存失败，不显示“已保存”；恢复服务后重新打开会比较版本并让你选择 | |
| U5 | 开两个标签页，A 新建需求，B（打开时早于 A）再改别的需求 | B 收到提示，页面恢复为数据库最新状态；B 被拒的修改在 `localStorage` 的备份键里 | |

| U7 | 删除一个已有任务的需求 | 需求从清单消失，任务保留 | |
| U8 | 导出 JSON → 再导入同一文件 | 无重复；不覆盖已有数据 | 页面代码已改为“预览→确认→提交”，应通过；**尚未在浏览器验证** |
| U9 | 导入一份**更旧**的备份 | 冲突被列出并默认跳过；已验收的任务不被重开 | 同上，应通过；旧的覆盖问题见修改记录 FND-04，页面已改走服务端导入器，**尚未在浏览器验证** |

## 三、在页面里检查功能清单是否完成

项目自带一份功能清单：[功能清单.json](功能清单.json)，格式就是页面能导入的备份。导入后用页面本身看进度，不用另找地方。

**第 0 步：用最新代码开一个独立实例**（不碰你正在用的数据）：

```powershell
$env:WORKBENCH_DATA_DIR = "$env:TEMP\workbench-checklist"
npm run dev -- --port 4190
```

**第 1 步：导入。** 打开 `http://127.0.0.1:4190` → 右上角“备份” → “↑ 导入 JSON” → 选 `docs/功能清单.json` → 看预览（应是需求新增 27、任务新增 27、冲突 0）→ 确认。

**第 2 步：怎么读。**

| 页面位置 | 看什么 |
|---|---|
| 需求清单 | 左侧“所属模块”筛选：`先做这一步`、`V1 功能`、`V1 收尾`、`V2 功能`。每行右侧显示该项的完成比例（已完成/总数 · 百分比），0% 的是还没验收，100% 的是你已点验通过 |
| 执行看板 | **待验收** = 已经做完、有自动测试，等你在页面点验；**已完成** = 你验过了；**待执行** = 还没做完（负责人在卡片上）；**待澄清** = 等你拍板；**阻塞** = 在等外部条件（写明了原因） |
| AI 协作任务 | 每个任务的“任务说明”就是**怎么检查**（步骤 + 期望结果），“AI 输出 / 处理结果”是自动测试证据。点“Run / 快照”可看启动时的快照 |

**第 3 步：逐项点验。** 按“怎么检查”操作；符合期望就在执行看板把那张卡从“待验收”改为“已完成”（会弹确认框）。不符合就改回“待执行”，并先在“AI 输出 / 处理结果”写一句哪里不对。

**说明：**

- “待验收”里有几项是**页面上看不到**的（本地接口防护、Runner 核心、文件范围冲突、AI 拆分接口），检查方法是运行 `npm test`。
- 清单是某一时刻的快照。之后有新进展，直接在页面里改状态；如果我或 Codex 更新了清单文件，重新导入只会**新增**新条目，已有条目不会被覆盖（冲突默认跳过）。
- 4179 端口上现在跑的是昨天启动的旧进程，需要重启才有新功能，见清单第 0 项。
